# Аудит служебных файлов — сентябрь 2026

Читались конфиги, сборка, деплой, зависимости, документация и скрипты. Продуктовый
код смотрелся только там, где он объясняет поведение конфига.

Ветка `audit/service-files`, единственный изменённый файл — этот. Ни одна находка не
починена: список нужен, чтобы резать его на задачи по одной, а не чтобы одним
заходом сделать двенадцать правок, из которых потом не отличить сломавшуюся.

**Как читать.** Находки отсортированы по отношению «последствие / цена», а не по
разделам: сверху то, что чинится за минуты и предотвращает реальный ущерб, снизу —
дорогое при небольшой пользе. В конце два раздела: что проверено и признано
нормальным, и что проверить не удалось с указанием причины.

**Стенд.** Локальный Docker недоступен (`docker ps` → «Cannot connect to the Docker
daemon»), поэтому всё, что требует базы, проверялось против **боевого** API
`https://api.groupmatch.app` и фронта `https://groupmatch.app`. Гостевые аккаунты
для проверок создавались через публичный `POST /api/v1/auth/guest` — тот же способ,
которым пользуется `scripts/smoke-test.sh`.

Из 30 находок **20 установлены запуском или командой** (curl к проду, `npm audit`,
`vitest`, `eslint`, `tsc`, `vite`, `smoke-test.sh`, git-команды, скрипты разбора
локалей и экспортов) — это находки 1, 2, 4, 5, 7–11, 13, 17, 18, 20, 21, 24–29.

## 1. `/actuator/metrics` открыт любому, кто сделал один анонимный POST

**Где:** `backend/src/main/resources/application.yml:57`,
`backend/src/main/java/com/groupmatch/config/SecurityConfig.java:109-141`

**Что:** в `management.endpoints.web.exposure.include` перечислены
`health,info,metrics`. В `SecurityConfig` `permitAll()` стоит только на
`/actuator/health` и `/actuator/info`, всё остальное закрывает
`.anyRequest().authenticated()` — **аутентификацией, а не ролью**. Роли `ADMIN` для
`/actuator/**` нет. При этом `POST /api/v1/auth/guest` публичный, не требует ни
почты, ни пароля и сразу отдаёт валидный access-токен.

То есть путь такой: один анонимный POST → токен → весь `/actuator/metrics`.
Проверено на проде, ответы получены:

```
POST /api/v1/auth/guest              → 201, accessToken
GET  /actuator/metrics               → 200, 100 имён метрик
GET  /actuator/metrics/disk.free     → 25631801344   (25,6 ГБ)
GET  /actuator/metrics/jvm.memory.max?tag=area:heap → 1494089728 (1,39 ГБ)
GET  /actuator/metrics/hikaricp.connections.max     → 20
GET  /actuator/metrics/system.cpu.count             → 1
GET  /actuator/metrics/http.server.requests         → список всех uri-шаблонов API
```

Без токена всё это отдаёт 401 — проверено отдельно по четырнадцати путям.

**Чем грозит:** наружу уходит карта приложения и его состояние: полный перечень
эндпоинтов с шаблонами путей (включая админские), свободное место, размер heap,
размер и занятость пула соединений, аптайм процесса, счётчики логов по уровням,
состав цепочки фильтров Spring Security. Это не эксплойт сам по себе — это
справочник для того, кто выбирает, что пробовать дальше, плюс готовый индикатор
эффекта: по `hikaricp.connections.pending` и `process.uptime` видно, подействовала
ли нагрузка и перезапускался ли контейнер. Отдельно неприятно, что `disk.free` и
`jvm.memory.*` позволяют оценить, сколько ещё выдержит стенд.

Внутренний потребитель у `metrics` сейчас отсутствует: мониторинга нет (это
записано в `docs/prod-runbook.md`, раздел «Открытые риски»), Prometheus не
подключён (`/actuator/prometheus` → 401 и не экспонирован).

**Цена починки:** минуты — убрать `metrics` из `exposure.include`. Если метрики
однажды понадобятся, правильный вид — оставить их в списке, но закрыть
`/actuator/**` ролью `ADMIN` в `SecurityConfig`, и тогда же добавить тест: сейчас
регрессию ловить нечем (см. находку 19).

**Проверено:** запуском — `curl` к `https://api.groupmatch.app` с токеном
гостевого аккаунта и без него; чтением — `application.yml` и `SecurityConfig.java`.

## 2. Любая ошибка маршрутизации и разбора отдаёт 500, и ничего не логируется

**Где:** `backend/src/main/java/com/groupmatch/exception/GlobalExceptionHandler.java:156-165`

**Что:** `@ExceptionHandler(Exception.class)` перехватывает всё подряд и возвращает
`500 server_error`. В него попадают штатные исключения Spring, у которых есть свои
коды: `NoResourceFoundException` (нет такого пути), `HttpRequestMethodNotSupportedException`
(не тот метод), `HttpMessageNotReadableException` (битое тело). Проверено на проде:

```
GET  /nope                              → 500 server_error   (ожидается 404)
GET  /api/v1/definitely-not-a-route     → 500 server_error   (ожидается 404)
GET  /actuator/env                      → 500 server_error   (ожидается 404)
PUT  /api/v1/me/plan                    → 500 server_error   (ожидается 405)
POST /api/v1/auth/signin, тело `{oops`  → 500 server_error   (ожидается 400)
```

Второе, и оно хуже: в классе **нет ни одной строки логирования**
(`grep -c 'log\.\|Logger' GlobalExceptionHandler.java` → `0`). Обработчик считается
успешным, поэтому Spring сам стектрейс тоже не печатает. Настоящее внутреннее
падение уходит в ответ строкой «An unexpected error occurred» и не оставляет следа
в логах.

**Чем грозит:** две вещи сразу.

Первая — 5xx перестают быть сигналом. Любой скан, любая опечатка в URL, любой
запрос от бота даёт 500. Когда появится внешний мониторинг (первый пункт бэклога),
он будет считать шум. Отличить настоящую аварию от чужого сканера будет нечем.

Вторая — `docs/prod-runbook.md` в комментарии к `show-details: never` обещает:
«Разбор „какой компонент лёг" теперь делается по логам приложения». Для ошибок
внутри обработки запроса это обещание не выполняется: логов нет.

**Цена починки:** часы. Логирование в catch-all — минуты, но добавлять его надо
вместе с отдельными обработчиками для трёх штатных случаев, иначе лог зальёт
стектрейсами от 404. Разумная форма — унаследоваться от
`ResponseEntityExceptionHandler` и оставить catch-all только для действительно
неожиданного, с `log.error`.

**Проверено:** запуском — пять `curl` к проду, коды и тела в ответах выше; чтением
— `GlobalExceptionHandler.java` целиком.

## 4. README обещает dev-сервер на 5173, он на 3000 — и CORS в README тоже 5173

**Где:** `README.md:61,83`, `README.ru.md:61,83`, `frontend/vite.config.ts:20`

**Что:** в обоих README написано `npm run dev # http://localhost:5173`, а в таблице
переменных бэкенда — `CORS_ALLOWED_ORIGINS | ... например http://localhost:5173`.
В `vite.config.ts` явно задан `server.port: 3000`, и дефолт в `application.yml:97` —
`http://localhost:3000`.

Проверено запуском: `npx vite` в `frontend/` печатает
`➜ Local: http://localhost:3000/`, `curl localhost:3000` → 200,
`curl localhost:5173` → соединение не устанавливается.

5173 — дефолт Vite, из которого проект ушёл; в README он остался.

**Чем грозит:** новый человек открывает 5173 и видит пустоту. Хуже второе: он
следует README и ставит `CORS_ALLOWED_ORIGINS=http://localhost:5173`, после чего
фронт на 3000 получает от бэкенда отказ CORS на каждый запрос — а выглядит это как
«не работает вход», без внятной ошибки. На отладку этого уходит вечер.

**Цена починки:** минуты — четыре числа в двух файлах.

**Проверено:** запуском — `npx vite` в `frontend/`, вывод и два `curl`.

## 5. Метрика прода противоречит записанному «открытому риску» про память

**Где:** `docs/prod-runbook.md:23,238-239`

**Что:** рунбук утверждает: таблица ресурсов — «Память | 1 ГБ», раздел «Открытые
риски» — «**1 ГБ памяти на JVM — впритык.** `-XX:MaxRAMPercentage=75.0` даёт heap
около 768 МБ. Под нагрузкой не измерялось, запас неизвестен».

Измерено на проде:

```
jvm.memory.max ?tag=area:heap  → 1 494 089 728   ≈ 1,39 ГБ
jvm.memory.used?tag=area:heap  →    97 887 840   ≈ 93 МБ (7 % heap)
system.cpu.count               → 1
```

Heap в 1,39 ГБ при `MaxRAMPercentage=75.0` означает контейнер примерно на 1,86 ГБ,
то есть **не 1 ГБ**. Почему так — из репозитория не видно: либо тариф подняли и
рунбук не обновили, либо расчёт «1 ГБ → 768 МБ» изначально не соответствовал
реальности. Это надо посмотреть в дашборде Timeweb, из этого окружения не видно.

**Чем грозит:** записанный риск сейчас ложный. Пока он висит в списке, кто-то либо
потратит деньги на увеличение памяти, которая уже есть, либо — что хуже — примет
решение «функцию не делаем, памяти впритык», опираясь на число, которое неверно
почти вдвое. Строчка «под нагрузкой не измерялось, запас неизвестен» тоже уже не
точна: базовое потребление измерено, это 7 % heap.

**Цена починки:** минуты на правку рунбука после того, как в дашборде подтвердится
фактический объём памяти контейнера.

**Проверено:** запуском — `curl` к `/actuator/metrics/jvm.memory.max` и `.used` с
тегом `area:heap` на проде.

## 6. `JWT_SECRET` имеет публичный дефолт и не проверяется при старте

**Где:** `backend/src/main/resources/application.yml:87`,
`backend/src/main/java/com/groupmatch/security/JwtUtils.java:19`

**Что:** `secret: ${JWT_SECRET:dev-secret-key-change-in-production-min-256-bits-12345678901234567890}`.
Значение по умолчанию лежит в репозитории открытым текстом. `JwtUtils` читает его
через `@Value("${jwt.secret}")` и никак не проверяет. `application-prod.yml`
`jwt.secret` не переопределяет — там только уровни логирования и `show-sql`.
Ни одной проверки на старте нет: поиск по `dev-secret` в `backend/src/main/java`
не даёт совпадений.

**Чем грозит:** если переменная `JWT_SECRET` когда-нибудь не доедет до контейнера —
опечатка в дашборде, потеря настроек при пересоздании приложения, миграция на
другую площадку — приложение **успешно стартует** и начинает подписывать токены
секретом, который лежит в публичном репозитории. Кто угодно выпускает себе токен с
любым `sub` и любой ролью, включая `ADMIN`. Внешне ничего не меняется: health
зелёный, логи чистые, пользователи входят.

Вероятность низкая, цена срабатывания — полный обход аутентификации, обнаружение —
случайное. Ровно тот класс дефекта, ради которого делают fail-fast.

Соседний `SPRING_DATASOURCE_PASSWORD:devpass` — та же схема, но там промах виден
сразу: приложение просто не подключится к боевой базе.

**Цена починки:** минуты. Достаточно проверки в `JwtUtils` (или отдельного
`@PostConstruct`), которая роняет старт, если активен профиль `prod` и секрет равен
дефолтному.

**Проверено:** чтением — `application.yml`, `application-prod.yml`, `JwtUtils.java`,
плюс `grep` по всему `backend/src/main/java`.

## 7. `v0.11.0` и `v0.12.0` выпущены мимо собственного чеклиста релиза

**Где:** git-теги, `frontend/package.json:4`, `backend/build.gradle.kts:9`,
`CHANGELOG.md:30`, `docs/release-process.md:97-110`

**Что:** `docs/release-process.md` требует три вещи — перенести накопленное из
`[Unreleased]` в секцию с датой, поднять версию в трёх файлах (четыре поля) и
поставить **аннотированный** тег. Для двух последних релизов не сделано ничего из
трёх:

```
v0.10.0 → fbe5c9d   package.json 0.10.0   build.gradle 0.10.0   CHANGELOG [0.10.0]   объект: tag
v0.11.0 → 0458644   package.json 0.10.0   build.gradle 0.10.0   CHANGELOG [0.10.0]   объект: commit
v0.12.0 → 5dd4fcf   package.json 0.10.0   build.gradle 0.10.0   CHANGELOG [0.10.0]   объект: commit
```

`git cat-file -t` для `v0.11.0` и `v0.12.0` возвращает `commit`, а не `tag` — теги
lightweight, без автора, даты и сообщения. У `v0.5.0`–`v0.10.0` — `tag`,
аннотированные, как и предписано.

`CHANGELOG.md` заканчивается секцией `[0.10.0] — 2026-08-19`; всё, что вошло в
`v0.11.0` и `v0.12.0` (серии слотов, выделение мышью и касанием, OG-превью,
отдельные точки входа под публичные страницы), лежит в `[Unreleased]`.

Отдельно: `docs/release-process.md:41-45` утверждает, что версия бэкенда «видна в
`/actuator/info`». Проверено на проде — `GET /actuator/info` возвращает `{}`.
`springBoot { buildInfo() }` в сборке не вызывается, `management.info.*` не
настроен, так что в `/actuator/info` версии нет и быть не может. Половина
утверждения про манифест jar при этом верна.

**Чем грозит:** ровно то, ради чего в `release-process.md` заводили теги — «а в
какой версии это сломалось» — снова не работает. Собранный артефакт трёх разных
релизов представляется как `0.10.0`; `/actuator/info` пуст; релиз-ноутов за два
релиза нет. При откате или разборе инцидента опереться не на что.

**Цена починки:** минуты на CHANGELOG и версии в трёх файлах (при следующем
релизе — заодно). Теги — отдельный разговор: `release-process.md:93-95` сам
предупреждает, что перезапись отправленного тега необратима для тех, кто уже сделал
`fetch`; здесь дешевле оставить как есть и записать это фактом, чем переставлять.

**Проверено:** запуском — `git cat-file -t`, `git show <tag>:<file>`,
`git for-each-ref`, `curl https://api.groupmatch.app/actuator/info`.

## 8. `ci.yml` объясняет вторую копию Dockerfile ссылкой на несуществующий `cd.yml`

**Где:** `.github/workflows/ci.yml:53-56`, `Dockerfile:6-9`, `backend/Dockerfile:6-9`

**Что:** комментарий к джобе `dockerfile-sync` говорит: файл лежит в корне «и в
`backend/` (исторический путь, **на него смотрит `cd.yml`**)». Такого workflow нет
и никогда не было в рабочем виде:

- в `.github/workflows/` лежит единственный файл — `ci.yml`;
- `grep -rn "cd\.yml"` по всему репозиторию даёт ровно одно попадание — эту самую
  строку комментария;
- по истории (`git rev-list --all` + `git ls-tree`) существовал
  `cd.yml.disabled` — то есть выключенный с рождения; добавлен в `1a14cd9`, удалён
  в `3fb4b0b`. Активного `cd.yml` в дереве не было ни в одном коммите.

Деплой действительно живёт вне GitHub Actions, и это в проекте описано: заголовок
`Dockerfile` говорит, что образ собирает Timeweb App Platform из корня репозитория,
`docs/prod-runbook.md:135-144` — что пуш в `main` запускает автодеплой Timeweb и
Vercel, а «`ci.yml` деплоем не управляет».

Сами копии сейчас идентичны: `cmp -s Dockerfile backend/Dockerfile` → совпадают,
джоба зелёная.

**Чем грозит:** вторая копия Dockerfile поддерживается ради потребителя, которого
нет, и комментарий останавливает любого, кто соберётся её убрать: там написано, что
на неё «смотрит cd.yml». Пока копии совпадают, вреда нет; вред начнётся в тот день,
когда кто-то поправит одну и упрётся в красную джобу с непонятным обоснованием.

**Цена починки:** минуты — переписать комментарий по факту. Удалять ли саму копию —
отдельное решение владельца: аргумент «вдруг платформа посмотрит туда» в заголовке
`Dockerfile` записан честно и от отсутствия `cd.yml` не рассыпается.

**Проверено:** запуском — `ls .github/workflows`, `grep -rn "cd\.yml"`,
`git rev-list --all` + `git ls-tree` по всем коммитам, `git show 3fb4b0b^:...`,
`cmp -s Dockerfile backend/Dockerfile`.

## 13. Ограничение частоты по IP не защищает от перебора — показано на практике

**Где:** `backend/src/main/java/com/groupmatch/filter/RateLimitFilter.java:104-134`,
`backend/src/main/resources/application.yml:120-130`

**Что:** корзина заводится по IP клиента (`bucketMap.computeIfAbsent(ip, ...)`),
`signin` — 10 в час. Проверка на проде: **20 подряд неверных попыток входа для
одного адреса почты — все 20 получили 401, ни одного 429.**

Причина установлена, и она важна для интерпретации: исходящий адрес этого окружения
не постоянен. Пять запросов к `api.ipify.org` вернули `160.79.106.128`, `.129`,
`.129`, `.136`, `.136`, ещё три — `.133`, `.142`, `.128`. То есть запросы
разошлись по пулу минимум из восьми адресов, и каждый попал в свежую корзину.

**Это не баг фильтра — фильтр работает как написан.** Но эксперимент показывает
цену модели «лимит на IP»: пул примерно из десяти адресов, который есть у любого
облака и у любого коммерческого прокси, превращает «10 попыток в час» в «100 в
час», и никаких дополнительных усилий для этого не требуется — у меня это вышло
непреднамеренно.

Второй слой защиты отсутствует: счётчика неудачных попыток на **аккаунт** нет.
Поиск по `backend/src/main/java` на `lockout|failed.?attempt|attempts` не даёт
совпадений; в `User` есть только `is_banned` и `is_blocked` — оба выставляются
администратором вручную.

**Чем грозит:** перебор пароля к конкретному аккаунту ограничен только терпением
атакующего. При этом в проде включён Argon2id
(`SecurityConfig`, `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`), и это
серьёзно замедляет перебор — но замедляет, а не останавливает, и заодно делает
перебор дешёвым способом нагрузить единственный vCPU.

**Цена починки:** переделка. Правильная форма — счётчик неудач на аккаунт с
экспоненциальной задержкой или временной блокировкой, поверх существующего лимита
по IP; хранить его есть где (Valkey уже используется для refresh-токенов и
чёрного списка). Это не однострочная правка и требует решений о поведении UI при
блокировке.

**Проверено:** запуском — 20 `POST /api/v1/auth/signin` с неверным паролем к проду
(коды ответов выше), восемь `curl` к сервисам определения внешнего IP; чтением —
`RateLimitFilter.java`, `User.java`, поиск по всему `backend/src/main/java`.

## 14. Корзины ограничителя растут без вытеснения

**Где:** `backend/src/main/java/com/groupmatch/filter/RateLimitFilter.java:30-33,110`

**Что:** четыре `ConcurrentHashMap<String, Bucket>` — по одной на `signup`,
`signin`, `refresh`, `invite-preview`. Запись создаётся
`computeIfAbsent(ip, k -> newBucket(capacity))` при первом запросе с адреса и
**никогда не удаляется**: ни TTL, ни ограничения размера, ни фонового вытеснения в
классе нет.

Три из четырёх путей публичные и не требуют авторизации: `POST /auth/signup`,
`POST /auth/guest`, `GET /api/v1/invites/{token}`. То есть любой адрес, обратившийся
к API один раз, оставляет в памяти процесса объект `Bucket` до перезапуска
контейнера.

**Чем грозит:** монотонный рост heap, который не откатывается. При IPv6 адресное
пространство практически неисчерпаемо (одна /64 — 2⁶⁴ адресов), так что источник,
способный менять исходящий адрес, наполняет карты со скоростью запросов. Heap в
проде — 1,39 ГБ (измерено, находка 5), занято сейчас 93 МБ, так что немедленной
угрозы нет, и заметить проблему без метрик тоже нечем: мониторинга нет. Итог —
процесс однажды упирается в OOM, платформа его перезапускает, причина не фиксируется
нигде.

**Цена починки:** часы. Замена `ConcurrentHashMap` на кэш с
`expireAfterAccess` (Caffeine) — небольшая правка, но добавляет зависимость;
альтернатива — периодическая чистка по расписанию, что дешевле по зависимостям, но
требует аккуратности с конкурентностью. Плюс тест, которого сейчас нет.

**Проверено:** чтением — `RateLimitFilter.java` целиком, поиск по классу на
`evict|expire|remove|clear|scheduled` — совпадений нет.

## 20. На фронтенде нет ни одного заголовка безопасности

**Где:** `frontend/vercel.json` (секции `headers` нет), `frontend/nginx.conf`

**Что:** ответ прода на `GET https://groupmatch.app/` содержит из относящегося к
безопасности только `strict-transport-security: max-age=63072000` (его добавляет
Vercel сам). Нет `content-security-policy`, `x-frame-options`,
`x-content-type-options`, `referrer-policy`, `permissions-policy`. Присутствует
`access-control-allow-origin: *` на HTML-документе.

В `vercel.json` секции `headers` нет вовсе — только `redirects` и `rewrites`. В
`nginx.conf` заголовков тоже нет, и там есть дополнительная тонкость: `add_header`
внутри `location` отменяет унаследованные, так что заголовки, добавленные на уровне
`server`, в блоке статики (`nginx.conf:19-22`) исчезли бы — это стоит держать в
голове, когда до заголовков дойдёт очередь.

Бэкенд при этом заголовки отдаёт — Spring Security по умолчанию:
`GET https://api.groupmatch.app/actuator/health` возвращает
`x-content-type-options: nosniff`, `x-frame-options: DENY`, `x-xss-protection: 0`,
`cache-control: no-store`. HSTS с бэкенда не приходит.

**Чем грозит:** без `x-frame-options`/`frame-ancestors` приложение можно поместить
в iframe на чужом сайте — классический clickjacking на действиях вроде «покинуть
группу» или «удалить встречу». Без `x-content-type-options` браузер угадывает тип
содержимого. CSP — самая полезная из недостающих и самая дорогая: она же ограничила
бы ущерб от XSS, к которому ведут уязвимости `react-router` из находки 18.

**Цена починки:** часы. `x-frame-options`, `x-content-type-options`,
`referrer-policy` — короткая секция `headers` в `vercel.json`, почти без риска. CSP
для React-приложения со сторонними шрифтами — отдельная работа с итерациями в
report-only режиме, иначе легко выключить половину интерфейса.

**Проверено:** запуском — `curl -I https://groupmatch.app/` и
`curl -D- https://api.groupmatch.app/actuator/health`; чтением — `vercel.json`,
`nginx.conf`.

## 21. Пул соединений на 20 при одном vCPU

**Где:** `backend/src/main/resources/application.yml:11-15`

**Что:** `hikari.maximum-pool-size: 20`, `minimum-idle: 5`. На проде измерено:
`hikaricp.connections.max` → 20, `hikaricp.connections.idle` → 5,
`hikaricp.connections.active` → 0, `system.cpu.count` → **1**.

**Чем грозит:** двадцать одновременных соединений к PostgreSQL на одном ядре — это
не «запас», а очередь: параллельно выполняться всё равно будет столько, сколько
позволяет процессор, а лишние соединения добавят переключений контекста на обеих
сторонах и займут память на стороне базы. Сколько соединений допускает тариф
PostgreSQL на Timeweb — из репозитория не видно; если предел близок к 20, то любая
вторая копия приложения (а автодеплой на короткое время держит две) упрётся в него.

Значение выглядит поставленным по умолчанию и с тех пор не пересматривавшимся.

**Цена починки:** часы, и начинать надо с измерения, а не с правки: `active`
сейчас 0, реальная одновременность неизвестна. Уменьшать вслепую — менять одно
необоснованное число на другое.

**Проверено:** запуском — `curl` к `/actuator/metrics/hikaricp.connections.*` и
`/actuator/metrics/system.cpu.count` на проде; чтением — `application.yml`.
`max_connections` самой базы проверить не удалось: доступа к ней нет.

**Что:** `frontend/Dockerfile` действительно использует `nginx.conf` — копирует его

вместо своих страниц.

просто rewrite, а переход на edge-функцию `frontend/api/og/join.ts`, которая ходит

принципе — там некому исполнять функцию. Предупреждение в рунбуке было написано до
появления OG-превью и с тех пор не дополнялось.

три страницы (это `location`-блоки, дело минут) и будут считать, что расхождений
больше нет. Превью ссылок в мессенджерах при этом молча перестанет работать —
именно молча, потому что для человека с браузером `/join/:token` продолжит
открываться нормально.

**Цена починки:** минуты на честное предупреждение в рунбуке. Реализация OG-превью
без Vercel — переделка (нужен серверный рендер или отдача заглушки бэкендом), и
делать её заранее незачем; достаточно, чтобы про неё знали.

**Проверено:** чтением — `frontend/Dockerfile`, `nginx.conf`, `vercel.json`,
`docs/prod-runbook.md`; запуском — проверка живого превью двумя `curl` с разными
User-Agent (см. находку 11).

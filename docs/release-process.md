# Процесс релиза

## Нумерация

SemVer с оговоркой: пока продукт не вышел из беты, старший разряд остаётся нулём —
`0.y.z`. Минорная часть растёт с каждым набором функций, патч — с исправлениями.
**`1.0.0` = выход из беты**, и никакого другого смысла у этого числа нет.

Слово «beta» в номер версии не входит. Оно живёт плашкой в интерфейсе, рядом со
словесным знаком (`frontend/src/shared/siteChrome.ts`, `Layout.tsx`). Причина
простая: статус беты — продуктовое решение, и меняется оно в один день по решению
владельца. Номер версии при этом меняться не должен, иначе `0.10.0-beta` придётся
переименовывать в `0.10.0` без единой правки кода — а сборки, теги и записи в
CHANGELOG уже разъедутся. Один факт — одно место хранения.

Отсюда же следует, что версия не содержит суффиксов `-rc`, `-beta`, `-alpha`
вообще: у проекта нет ни канареечного контура, ни staging (см.
`docs/prod-runbook.md`, раздел «Открытые риски»), так что предрелизных сборок,
которые надо было бы отличать, не существует.

## Где живёт номер версии

Три файла, четыре поля — все обязаны совпадать:

| Файл | Поле |
|---|---|
| `frontend/package.json` | `version` |
| `frontend/package-lock.json` | `version` (корневое) |
| `frontend/package-lock.json` | `packages[""].version` |
| `backend/build.gradle.kts` | `version` |

Второе поле в lock-файле забывают чаще всего: `npm` его не синхронизирует, если
править `package.json` руками, и расхождение всплывает при следующем `npm ci`.
Проверка после правки:

```bash
grep -rn '"version"' frontend/package.json frontend/package-lock.json | head -3
grep -m1 '^version' backend/build.gradle.kts
```

Номер версии бэкенда попадает в манифест собранного jar
(`Implementation-Version`) и виден в `/actuator/info`. Имя файла артефакта при
этом от версии не зависит — оно зафиксировано как `app.jar`
(`bootJar.archiveFileName`), иначе команда запуска на платформе ломалась бы при
каждом повышении версии.

## Теги

Тегов в репозитории до 0.10.0 не было ни одного: «что сейчас в проде»
отслеживалось по коммитам мержа в `main`. Это работало ровно до первого вопроса
«а в какой версии это сломалось».

Тег ставится **на коммит мержа в `main`**, не на коммит в `develop`: в прод едет
именно то, что оказалось в `main`, и тег должен указывать на тот же объект,
который собрала платформа.

### Текущий релиз

```bash
git checkout main && git pull
git tag -a v0.10.0 -m "Release 0.10.0"
git push origin v0.10.0
```

### Теги задним числом

Границы релизов установлены по истории. Команды готовы к запуску, **в этой задаче
они намеренно не выполнялись** — теги ставит владелец репозитория:

```bash
git tag -a v0.6.0 01530f0 -m "Release 0.6.0"
git tag -a v0.7.0 7098625 -m "Release 0.7.0"
git tag -a v0.8.0 49714a6 -m "Release 0.8.0"
git tag -a v0.9.0 e2f0bb8 -m "Release 0.9.0"
git push origin v0.6.0 v0.7.0 v0.8.0 v0.9.0
```

⚠️ Проверить перед push: `git tag` показывает только локальные теги, а
`git push origin <tag>` необратим для тех, кто уже сделал fetch. Перепутанный
коммит проще не отправлять, чем потом рассылать команде `git tag -d`.

Релизы `0.1.0`–`0.5.0` тегами не покрываются: границы по истории восстанавливаются
неоднозначно, а `0.5.0` в `CHANGELOG.md` отсутствует вовсе (см. «Нашёл по дороге»
в отчёте по этой задаче).

## Чеклист релиза

1. **CHANGELOG.md** — перенести накопленное из `[Unreleased]` в новую секцию с
   датой. Писать, что изменилось для пользователя; «как сделано» — в `Technical`.
2. **Версия** — поднять в трёх файлах (четыре поля, таблица выше).
3. **Мерж в `main`** — через PR из `develop`.
4. **Тег** — на коммит мержа, командой выше.
5. **Автодеплой Timeweb** — начинается по пушу в `main` сам. Проверить в дашборде,
   что сборка прошла: «Логи деплоя», затем «Логи приложения» — в них должно быть
   `Schema "public" is up to date` (если миграций не было) и `Started
   GroupmatchApplication`. Фронт на Vercel деплоится параллельно и независимо.
6. **Smoke-test**:
   ```bash
   ./scripts/smoke-test.sh https://api.groupmatch.app https://groupmatch.app
   ```
7. **Проверить из российской сети без VPN** — ради этого и был переезд с прежней
   площадки; автоматикой не покрывается.

Между шагами 3 и 5 отката нет: платформа начинает сборку сразу по пушу. Если
релиз рискованный, откат — это `git revert` мержа и повторный пуш в `main`, то
есть ещё один полный цикл сборки (порядка нескольких минут).
